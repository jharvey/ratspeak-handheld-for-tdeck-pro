DEVICE FACTS
------------
PSRAM: found=1 size=0 — use INTERNAL only; Settings shows "PSRAM n/a".
Heap: ~45K post-proto; ~28K post-LVGL (10-line strip); ~24K steady after UI.
Touch: CST328 @ 0x1A (not GT911). Minimal 0xD000 finger-1 read in
  StandaloneApp — no SensorLib dependency. Soft-fail keeps INT-only next.
Outbound: lxmfSubmit to selected MsgRow peer (g_selPeer).
Compose: 120-char buffer; idle ~1.6s one fullRefresh for footer ">text".
Peer: serial/kb p cycles; Messages list shows >; History mark-reads sel.
  E23 also fills free rows from AnnounceManager::nodes() as "(ann ...)" targets.
Keyboard shortcuts (compose empty only): a=announce t=ping H=history p=peer.
  Leading space avoids H/t/a/p swallowing first letter of a message.

SERIAL HINTS (line + Enter)
---------------------------
  t / t hello / t:hi   send to selected peer
  H                    toggle History (marks read)
  p                    cycle selected peer
  c                    clear compose buffer
  a r n h m s / 1 2 3  announce / reload / next / home / msgs / settings

KEYBOARD HINTS
--------------
  type + pause ~1.6s   compose on glass footer
  Enter (nonempty)     send to selected peer
  Enter (empty)        next screen
  a / t / H / p        shortcuts only when compose empty
  (type a space first if message should start with H/t/a/p)

TOUCH HINTS

  Messages peer row    select that peer; STAY on Messages (even if same peer)
  Messages header/foot next screen
  History any tap      back to conversation list
  Home / Settings      next screen

E-INK REFRESH (GDEQ031T10 / GxEPD2)
-----------------------------------
Panel: Good Display GDEQ031T10 240x320, controller via GxEPD2_310_GDEQ031T10.

Theory (Applied Science / Krasnow "E-paper hacking: fastest possible refresh"):
  - Full waveform = long multi-phase drive; particles fully settled; flashes.
  - Partial / differential = compare new vs previous buffer; drive only deltas.
  - Speed comes from shorter LUTs (lookup tables / waveforms). Tradeoff:
    less contrast, ghosting builds unless a full clean is done periodically.
  - Practical rule from Good Display / LilyGO for this panel:
      after ~5 consecutive fast or partial refreshes, do one full refresh.

GxEPD2 already supports this panel (no extra library required):

  hasPartialUpdate       = true
  hasFastPartialUpdate   = true
  useFastFullUpdate      = true   // shorter full; disable for cold temps
  full_refresh_time      ~ 1100 ms
  partial_refresh_time   ~ 700 ms

  API surface used today / available next:
    g_epd.setFullWindow();   firstPage/nextPage  -> full refresh (current path)
    g_epd.setPartialWindow(x,y,w,h); firstPage/nextPage -> partial region
    refresh(false) full, refresh(true) partial (higher-level helpers)

DisplayEink today:
  fullRefresh() only — setFullWindow + drawBitmap of whole FB.
  refreshIfDirty() always calls fullRefresh().
  Policy: one fullRefresh per screen change (Home/Msgs/Settings/History).

Recommended future policy (E24 optional partial experiment):
  1. Screen *change* (Home <-> Msgs <-> Settings, enter/leave History)
       -> fullRefresh (clean slate).
  2. In-place updates (compose footer, peer ">" marker, unread count)
       -> partialRefresh of dirty region (or full window partial).
  3. Keep a partial counter; every N (default 5) partials force one full.
  4. Do not invent custom LUTs first — stock GxEPD2 fast/partial is enough
       to trial. Custom waveforms only if ghosting is unacceptable.
  5. After hibernate / long power-off, first update must be full (previous
       buffer may be invalid for differential).

Reference:
  https://www.youtube.com/watch?v=MsbiO8EAsGw  (Krasnow LUT / partial)
  http://benkrasnow.blogspot.com/2017/10/fast-partial-refresh-on-42-e-paper.html
  Good Display GDEQ031T10 notes: full / fast / partial; full after 5 partials
  GxEPD2: src/gdeq/GxEPD2_310_GDEQ031T10.h
