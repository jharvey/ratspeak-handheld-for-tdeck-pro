DEVICE FACTS
------------
PSRAM: found=1 size=0 — use INTERNAL only; Settings shows "PSRAM n/a".
  Hardware is 8MB OPI; size=0 = board/build map not active. Fix is
  platformio/board flags + probe, not app archaeology. Defer until
  after energy phase or only as a focused experiment.
Heap: ~45K post-proto; ~28K post-LVGL (10-line strip); ~24K steady after UI.
Touch: CST328 @ 0x1A (not GT911). Minimal 0xD000 finger-1 read in
  StandaloneApp — no SensorLib dependency. Soft-fail keeps INT-only next.
Outbound: lxmfSubmit to selected MsgRow peer (g_selPeer).
Compose: 120-char buffer; idle ~1.6s one fullRefresh for footer ">text".
Peer: serial/kb p cycles; Messages list shows >; History mark-reads sel.
  E23 also fills free rows from AnnounceManager::nodes() as "(ann ...)" targets.
Keyboard shortcuts (compose empty only): a=announce t=ping H=history p=peer.
  Leading space avoids H/t/a/p swallowing first letter of a message.
Battery: ~1400-1500 mAh LiPo. E-ink refresh energy is negligible at messaging
  rates; always-on MCU + continuous LoRa RX dominate (see ENERGY ROADMAP).

E-INK REFRESH (GDEQ031T10 / GxEPD2)
-----------------------------------
Panel: Good Display GDEQ031T10 240x320, controller via GxEPD2_310_GDEQ031T10.

Theory (Applied Science / Krasnow "E-paper hacking: fastest possible refresh"):
  - Full waveform = long multi-phase drive; particles fully settled; flashes.
  - Partial / differential = compare new vs previous buffer; drive only deltas.
  - Speed comes from shorter LUTs (lookup tables / waveforms). Tradeoff:
    less contrast, ghosting builds unless a full clean is done periodically.
  - Practical rule from Good Display / LilyGO for this panel:
      after ~5 consecutive fast or partial refreshes, do one full refresh.

GxEPD2 already supports this panel (no extra library required):

  hasPartialUpdate       = true
  hasFastPartialUpdate   = true
  useFastFullUpdate      = true   // shorter full; disable for cold temps
  full_refresh_time      ~ 1100 ms
  partial_refresh_time   ~ 700 ms

  API surface used today / available next:
    g_epd.setFullWindow();   firstPage/nextPage  -> full refresh (current path)
    g_epd.setPartialWindow(x,y,w,h); firstPage/nextPage -> partial region
    refresh(false) full, refresh(true) partial (higher-level helpers)

DisplayEink today:
  fullRefresh() only — setFullWindow + drawBitmap of whole FB.
  refreshIfDirty() always calls fullRefresh().
  Policy: one fullRefresh per screen change (Home/Msgs/Settings/History).

Recommended UI policy (E24 optional partial experiment):
  1. Screen *change* (Home <-> Msgs <-> Settings, enter/leave History)
       -> fullRefresh (clean slate).
  2. In-place updates (compose footer, peer ">" marker, unread count)
       -> partialRefresh of dirty region (or full window partial).
  3. Keep a partial counter; every N (default 5) partials force one full.
  4. Do not invent custom LUTs first — stock GxEPD2 fast/partial is enough
       to trial. Custom waveforms only if ghosting is unacceptable.
  5. After hibernate / long power-off, first update must be full (previous
       buffer may be invalid for differential).

Panel energy (5 msg/day scale): ~11 mW during refresh, ~0.017 mW standby.
  Full ~0.001 mAh/update; partial slightly less. Negligible vs radio/MCU.
  Partial is a UX win, not a battery tradeoff at messaging rates.

Reference:
  https://www.youtube.com/watch?v=MsbiO8EAsGw  (Krasnow LUT / partial)
  http://benkrasnow.blogspot.com/2017/10/fast-partial-refresh-on-42-e-paper.html
  Good Display GDEQ031T10 notes: full / fast / partial; full after 5 partials
  GxEPD2: src/gdeq/GxEPD2_310_GDEQ031T10.h

ENERGY ROADMAP (after messaging is solid)
-----------------------------------------
Do this only when bring-up is "basically running" (E23-level: TX/RX, compose,
peer select). Goal: stretch 1400-1500 mAh from ~1-3 days always-on toward
many days / weeks at low message rates. Keep cooperative green; optional
compile flag or serial command to disable sleep while debugging.

Why energy work is separate:
  - Current standalone loop is always awake: proto.loop + continuous LoRa RX.
  - E-ink refresh is NOT the drain (see above). MCU + SX1262 RX are.
  - Sleep changes timing, IRQ paths, and protocol assumptions — easy to
    break messaging if done mid-bring-up.

Dominant loads today (order of magnitude):
  ESP32-S3 active + protocol loop   ~20-40 mA
  SX1262 continuous receive         ~5-10 mA
  E-ink standby / rare refresh      ~uA / bursts
  -> Always-on class runtime: about 1-3 days on 1500 mAh.

Phased energy work (suggested order):

  F1  Measure baseline
      - Log free_int is not enough: add periodic battery % / mV (BQ27220).
      - Optional: serial "power" line with last RSSI, uptime, bat.
      - Know before/after when changing sleep.

  F2  Idle light-sleep between loop work
      - When no key/touch/serial/pending TX and radio quiet for N ms,
        esp_light_sleep or timed delay with radio still in RX if needed.
      - Wake sources: TCA8418 INT, CST328 INT, SX1262 DIO, timer.
      - Must not starve proto.loop / lxmfPoll / announce.loop.

  F3  Radio duty-cycle / WOR (biggest win)
      - Continuous RX is the long-term killer.
      - Prefer SX1262 duty-cycle RX or wake-on-radio where protocol allows.
      - Document impact on latency (message may wait for next RX window).
      - Keep a "always listen" debug mode for field tests.

  F4  Deep sleep between sparse sessions (optional, aggressive)
      - Only if product goal is rare check-ins, not interactive messenger.
      - Hibernate e-ink (GxEPD2 hibernate); cold-sleep radio; deep sleep MCU.
      - Wake: timer, or GPIO from radio/keyboard.
      - First e-ink update after wake must be full refresh.
      - Protocol state must survive or re-init cleanly from flash.

  F5  Peripheral power gates
      - BOARD_GPS_EN, BOARD_1V8_EN, BOARD_LORA_EN, BOARD_6609_EN already
        defined — gate GPS/audio/unused rails when idle.
      - Do not cut LoRa or e-ink power while session active.

  F6  UI policy that helps energy
      - Partial refresh for in-place updates (E24) — small win, better UX.
      - Avoid auto fullRedraw storms (already rate-limited).
      - Dim/disable unnecessary live counters when idle.

  F7  PSRAM (optional, parallel experiment)
      - size=0 today; OPI 8MB on silicon. Fix board_build qio_opi + probe
        sketch before moving protocol node to SPIRAM.
      - Not required for energy; required for larger protocol profiles.

Expected outcomes (rough, not measured on this unit):
  - Always-on RX (today):           ~1-3 days
  - Light-sleep + duty-cycled RX:   many days at 5 msg/day
  - Deep sleep + rare wake:         weeks+ (interactive UX suffers)

Never claim a runtime number without a measured baseline on the same
firmware + battery %.
