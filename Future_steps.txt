Security: password, accounts, encrypted storage (user asked 2026-11-12)
-----------------------------------------------------------------------
- Now (ui-features branch): one device password; turning the lock on asks for the password
  and a confirmation; no lock without a password.
- Messages encrypted at rest under the password. Design: a random 256-bit data key (DEK)
  encrypts every message record (AES-256-GCM, per-record nonce). The DEK is stored only
  wrapped by a key derived from the password (PBKDF2/Argon2-style KDF, salt, high iteration
  count). No password set = DEK wrapped by a built-in default password, so the format is the
  same either way.
  - Setting or changing the password re-wraps the DEK only: instant, no messages lost, no
    need to re-encrypt every record. (Re-encrypting all records with a new DEK is optional,
    e.g. after a suspected leak, done in the background like the folder migration.)
  - First boot of the encrypting firmware: existing plain-text records are encrypted once
    (migration at boot, like the shard move).
  - Unlock at boot / after idle derives the key; while locked, incoming messages are still
    received: store them sealed to a public key (X25519) so they can be written without the
    password and opened after unlock.
  - Covers flash and the SD archive. Identity / ratchet keys: decide whether they also go
    under the DEK (then nothing decrypts or announces until the first unlock after boot).
  - Forgotten password = messages are unrecoverable (say so in the UI); factory reset only.
- User accounts (later): several users per device, each with its own password, DEK,
  contacts and messages (and possibly own LXMF identity); one admin.

Team awareness, ATAK-style (user asked 2026-11-12, longer term)
---------------------------------------------------------------
- Builds on "share my location" (position text + LXMF location field) and the offline map.
- Relative markers: "something interesting 600 ft north of me". Make a marker by distance +
  direction from my position (or by moving a cursor on the map), with a type (hazard, person,
  vehicle, camp, water, meet-up, other) and a short note; send it to a contact or group. The
  receiver sees it on the map and as text with distance + bearing from THEIR position
  ("hazard, 0.4 mi NE of you").
- Contacts on the map: last shared position of each contact with its age; list sorted by
  distance with bearing arrows; optional periodic position sharing (opt-in, interval, to
  chosen contacts only; respects energy modes / check-in windows).
- Waypoints / navigation: "go to" a marker: distance + bearing on screen; heading from GPS
  course over ground (no magnetometer, see Map heading).
- Navigate to a contact (user asked 2026-11-12, e.g. hunting: "son is over that way 900 ft"):
  needs the contact's auto-shared position. "Go to contact" screen: distance, compass
  direction + degrees ("900 ft NE, 45 deg"), age of their last fix; an arrow relative to
  your direction of travel while walking (GPS course; unreliable when slow/still); both on
  the map, north up. Alert when they stop sharing / fix gets old. True facing direction
  while still needs a magnetometer: confirm none on the board (I2C scan), else consider an
  add-on magnetometer board.
- Units setting (ft/mi or m/km), lat/lon or MGRS grid.
- Interop: compact binary location/marker field in LXMF (Sideband-compatible telemetry where
  possible); later a gateway to ATAK / TAK (Cursor-on-Target XML) so phones running ATAK
  see the T-Deck units and their markers.
- Privacy: nothing shared automatically by default; clear "sharing on" indicator.

Home Assistant integration (user asked 2026-11-12)
--------------------------------------------------
- Presence detector: HA knows when the handheld (its owner) is home / away. Routes, cheapest
  first: (1) home gateway (Pi + RNode running Reticulum) hears the unit's LoRa announces /
  check-ins and reports "seen in the last N min" to HA (MQTT); works with WiFi off and long
  range; (2) unit joins home WiFi -> HA sees it (router / MQTT birth message); (3) BLE beacon
  for room-level presence (ESPresense / Bermuda), costs battery.
- Trigger things: send commands from the handheld (e.g. "garage open", a scene) as LXMF
  messages to an HA bridge identity; the bridge allows only known source hashes (contacts
  list) and replies with the result. A MENU / quick-action screen for saved commands.
- HA -> handheld: HA automations send alerts / notifications to the unit over LXMF (works
  off-grid via the LoRa gateway, e.g. doorbell, water leak, alarm armed).
- Optional: report battery / GPS position to HA as sensors (opt-in, privacy).
- Needs: a small bridge (Python, Reticulum + MQTT or an HA custom integration) on the home
  gateway; message format for commands (plain text first, then a field-tagged LXMF type).
